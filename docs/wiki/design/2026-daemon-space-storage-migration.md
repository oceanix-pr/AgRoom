# Daemon 运行凭证按空间分区迁移设计

> 状态：新运行按 `personal/`、`work/` 分区与双来源读取已实现；交接与空间隔离宿主回归已通过。旧共享根的只读递归盘点器、单空间数据库身份探针、只读预检计划器及新版 Store 的短时跨进程变更锁已实现。预检候选不授权迁移，旧版进程也不识别新锁。旧根内容的整组迁移、兼容路径移除和真实跨进程崩溃故障注入仍未完成。以下同时保留已落地协议与后续迁移设计，不能把新写入分区误读成历史运行凭证已迁净。实现事实以 `DaemonHandoffStore`、`DaemonLegacyInventory`、`DaemonLegacyMigrationPlanner`、`SessionService`、`DaemonMain`、`ChatView` 和 [01-项目与架构](../01-项目与架构.md) 为准。

## 问题与优先级

`DaemonHandoffStore.standard` 的全局根仍位于 `~/Library/Application Support/AgRoom/daemon/`，但新 `run-<id>.json`、`owner-<id>.json`、`run-<id>/operations.json` 及隔离证据已写入固定的 `personal/` 或 `work/` 子目录。完整 `EngineRunSnapshot` 含系统、用户、助手和工具结果文本，工具参数 JSON、图片、思考与轨迹；`settings` 还可能含人设、工作区路径、授权范围和资源上下文。日志回执也可能含私有内容，故分区不只针对数据库。全局根仍可能留有旧 `run-`、`handoff-`、`owner-`、journal 与 `quarantine/` 内容。

新记录已按空间物理分区；读取器同时扫描两空间及旧根，Daemon 写回按 `record.space` 选库，并对来源、owner 和正文身份交叉核对。旧根残留仍不满足“所有历史隐私内容都在所属空间目录”的目标；同一 macOS 用户也仍可访问两个空间的文件，分区并不提供加密保密边界。

| 优先级 | 风险 | 当前处理与剩余边界 |
|---|---|---|
| P1 | 旧根明文快照、工具回执与损坏证据仍可能混放。 | 新记录按空间落盘，旧任务按来源原地收尾；旧证据受控迁移待实施。 |
| P1 | 旧 Daemon 持锁时，新 App 交接记录可能只被新版本识别；同空间旧新双份不得任选一份运行。 | App 等待新 Daemon 的随机 token READY；新进程打开同一锁并待命，取得锁后重扫两种布局。同空间双份与来源不明先失败关闭。READY 只证明进程当时进入待命路径，不保证它之后存活或完成任务。 |
| P2 | 全局根的 owner 与未经归属的进程输出可能泄露空间身份。 | 新 sidecar 随运行进入空间目录；Daemon 原始 stdout/stderr 不再追加到共享 `daemon.log`。旧根 owner、旧日志文件若已存在仍待清理。 |

同一 macOS 用户仍可访问两个空间目录；本方案解决应用的物理分区与误路由，不把目录分区描述为操作系统级保密或加密边界。

## 目标布局

为减少首批代码改动，保留现有文件名和每运行 journal 目录，仅在它们上方增加固定空间目录：

```text
~/Library/Application Support/AgRoom/daemon/
  daemon.lock                         # 全局单实例协调；仅 PID/锁状态
  store.lock                          # 新版 Store 短时文件变更互斥
  layout.json                         # 可选：协议版本，不含运行或空间身份
  personal/
    run-<id>.json                     # personal 的完整快照与设置
    owner-<id>.json                   # 同一运行的恢复身份
    run-<id>/operations.json          # 父层 journal；未来子记录也在此目录下
    quarantine/                       # 损坏及人工放弃证据
  work/
    run-<id>.json
    owner-<id>.json
    run-<id>/operations.json
    quarantine/
  run-<legacy-id>.json                # 仅过渡期读取的旧根记录，不再新建
  handoff-<legacy-id>.json            # 仅过渡期读取的旧格式
  owner-<legacy-id>.json              # 旧记录的 sidecar
  run-<legacy-id>/                   # 旧记录的 journal
  quarantine/                         # 旧损坏证据；归属未知时保持隔离
```

`AppSpace` 只映射代码中固定的 `personal`/`work` 路径段；不从快照、工具参数或外部字符串拼目录。新记录的 owner、正文、journal、未来嵌套子代理快照和隔离证据必须全在**同一空间目录**。根目录只应长期留下无空间内容的锁和布局版本；若仍有归属未知的旧证据，不能宣称迁移完成。

App 现将 Daemon 的普通 stdout/stderr 指向空设备；只有 relay 的版本化随机 token READY 经管道返回，原始输出不再追加到共享 `daemon.log`。旧日志文件如已存在仍属旧根残留。全局锁继续共用，不能改成每空间一个而允许两个 Daemon 同时领取旧记录。

## API 与身份契约

- 把新记录的路径入口改为 `recordFileURL(id:space:)`、`ownerFileURL(id:space:)`、`runDirectory(id:space:)`、`recordStatus(id:space:)`、`recordPresence(id:space:)`、`updateState(id:space:to:)`、`removeRecord(id:space:)`。新建 `writeRecord(_:)` 从可信 `record.space` 选目录；已有记录的更新走 `writeRecord(_:at:)` 或等价的 `LocatedRecord` API，保留原来源。两条路径都验证文件内 `id/space/sessionId/assistantMessageId` 与 owner 一致；不按相同 UUID 搜索另一空间回退。
- App 和任务中心用 `records(in:)`、`quarantinedEvidence(in:)` 等空间限定读取；全局 `ownershipSnapshot()` 只向空间 UI 提供该空间的阻挡集合及无法归属的协调标志，不返回另一空间正文或证据路径。运行身份键是 `(space, id)`，会话占有身份键是 `(space, sessionID)`；Daemon 的领取、已尝试集合和去重也使用复合键。两空间使用相同 UUID 是两个独立运行。Daemon 可以在进程协调层遍历 `AppSpace.allCases`，但交给执行器的是带来源目录的 `LocatedDaemonRecord`；`record.space` 与来源目录不符即转人工，不能以记录字段改选另一目录。
- 当前生产 Daemon 使用带来源的定位记录，任务中心使用空间限定读取。`DaemonHandoffStore` 已移除无空间参数的 `records()`、`actionableRecords`、`recoveryRequiredRecords` 与全局会话 ID 便利属性；`OwnershipSnapshot` 和 Supervisor 只公开按空间键控的会话集合及无身份的进程协调布尔值，避免新 UI 误用两空间合并的完整快照或会话 ID。
- 旧根记录带明确 `.legacyRoot` 来源；状态更新、journal 写入、隔离和删除都继续落在**该来源**，不能把 `updateState` 的一次调用意外变成新目录写入。新 App 交接只能建 `.space(personal/work)` 记录；旧根只供已有任务收尾和受控迁移。
- owner 先原子写入并确认，再写运行正文；任何一步失败保留已有文件。只有 owner 无正文也算未完成凭证，必须阻止同一会话新运行，不能当作空目录。新空间目录内的 owner 缺失、身份不匹配、未知版本或正文损坏都保留文件并进入人工恢复。目录和文件分别设为仅当前用户可读写；不靠文件权限替代空间字段核对。
- 全局监督仍可汇总“是否有待执行任务”和“是否有无法归属的旧证据”两个协调信号；不向某一空间 UI 返回另一空间的记录、会话 ID 或证据路径。无法归属的旧证据只给全局阻塞信号与人工处理入口，不猜测归属。

旧 `DaemonHandoff` 文件可能没有 owner sidecar；兼容读取只能维持既有旧记录的恢复路径，不能据此为新记录放宽 owner 契约。未来 [子代理持久恢复设计](2026-daemon-nested-agent-recovery.md) 中的父/子路径应随此布局落在同一空间，不能沿用其当前示意图的共享根。

## 渐进实施与迁移顺序

1. **失败关闭门禁（源码与宿主回归已实施，真实跨进程故障注入待验）。** `DaemonHandoffStore` 返回“空间 + 来源”定位结果；扫描根与两空间目录时，同一 `(space, id)` 旧新重复、owner/正文不匹配、路径空间和正文空间不一致均不进入可执行队列。扫描不移动损坏原件，原位文件与旧隔离区都参与阻挡；空间限定记录候选只读所属目录和旧根，全局纯读审计同步提供跨目录异常的失败关闭信号。同 UUID 分属两个空间是独立运行。无法归属的旧证据继续全局阻塞；已归属及分区内未知证据有受限人工入口，同空间重复凭证只显示人工核对警示。
2. **新写入分区（源码与宿主回归已实施，真实进程级握手待验）。** App 新交接只落 `personal/` 或 `work/`，Daemon 后续状态/journal 按来源路由，旧根记录原地运行至终态或人工恢复。旧 Daemon 可能持全局锁时，App 启动新版 relay 并等待随机 token READY；relay 在已打开固定锁 inode、即将阻塞等待旧进程时回应。旧进程释放锁后 relay 取得锁并重扫所有来源；READY 后崩溃仍可能使任务留待下次监督，不能当成完成保证。
3. **清理可确认的旧证据。** 活跃旧任务不移动，也不在迁移期间执行外部工具。待旧 Daemon 停止、App 和新 Daemon 的交接/状态写入都服从同一短时跨进程存储锁后，逐条核验旧根正文、owner、journal 和会话归属。已完成且无需保留的记录按现有完成规则删除；`recoveryRequired` 或可归属的隔离证据按整组复制到所属空间的临时目录，逐文件校验长度与摘要，再移入空间目录。迁移开始前和结束后扫描旧/新路径；中断留下同一 `(space, id)` 双份、半份或摘要不一致时保持不可执行和会话阻塞，绝不优先选其中一份。完整核对并确认空间副本可发现后才删除旧副本。迁移锁只包短文件操作，不在锁内请求模型、执行工具或做 UI 回调。
4. **处理无法归属的旧文件。** 缺失/损坏 owner 且正文也不可核对，或旧 `handoff` 无法可信确定空间时，原件留在旧根原位或既有受限隔离区并保持全局发送阻塞，交由用户核实；不按文件名、UUID、工作区路径或当前 UI 空间推断归属。现有人工放弃只把证据移到旧根 `quarantine/abandoned/`，可解除运行阻挡，**不等于物理迁净**。用户确认归属后才可移入对应空间；归属不能确认时应明确选择保留、导出或删除，不能以「已放弃续跑」推定允许删除。只有递归审计证明共享根不再含私有字节，才移除兼容执行路径和全局内容扫描，并更新 01/05/10 及子代理设计的布局图。

多文件迁移不能依赖单个 `Data.write(.atomic)` 伪装为原子事务。迁移复制期间目标临时文件不进入可执行扫描；如果同一 `(space, id)` 的旧副本与目标正式副本并存，扫描器必须拒绝自动执行。恢复时只能在完整身份、摘要、来源与迁移状态一致后继续清理，不能利用“新文件看起来完整”自动重放旧运行。存储介质不可读/不可写时保留原字节，不能把失败视为缺记录。

**启用步骤 3–4 的前置条件：**纯读的 `DaemonLegacyInventory` 已独立递归盘点 `run`/`handoff`/`owner`、每运行 journal、`quarantine/abandoned/`、迁移临时文件和旧 `daemon.log`，拒绝符号链接、未知文件类型、硬链接及归属冲突；按文件大小、总读取量、条目和深度限制资源。报告只在 owner、正文和日志身份一致时给出**文件级佐证**，尚未核对空间数据库，也不自动清理或搬迁。常规运行扫描不能代替这个盘点。新版 Store 的创建、状态更新、隔离、删除及人工放弃已使用固定 inode 的短时 `store.lock`；人工放弃先非阻塞取得 `daemon.lock`，再取得 `store.lock`，不跨数据库 `await` 持锁，并在返回后重新核对原证据。空间目录及日志文件异常时失败关闭。后续仍须让扫描识别持久迁移标记，复制与摘要计算在锁外。旧版 App/Daemon 和 `IdentityMigration` 不识别新锁，迁移仅能在可证明它们已停且不能并发重启的升级窗口启动；迁移者还须非阻塞取得现有 `daemon.lock`，旧 Daemon 正运行就延后。

可信整组先核对 owner、正文、空间库归属与目标冲突，再把文件清单、长度和 SHA-256 写入所属空间的受限 staging manifest。发布标记后复制、逐项校验与同步落盘；正式发布及旧组清理分步完成，任一步失败均保留可核对原字节并阻止自动续跑。重启时按 manifest 对账，不把内容移回共享根，也不因目标副本存在而重放未知副作用。首批只处理已终态且可清理的组，以及 `recoveryRequired` 或可信已归属的隔离组；活跃旧任务留在原来源收尾。完整迁移须以两个真实进程和各复制、发布、删除中断点的故障注入验收。

### 旧版本写者与维护窗口门禁

**现有固定 `daemon/` 根及两把锁不足以证明旧 App 不会重启写入。**旧版 App 不取得 `store.lock`，也不识别未来的迁移 marker；它可能在进程检查之后由登录启动、另一份安装包或开发覆盖路径重新运行。`daemon.lock` 只排除持有同一 inode 的旧 Daemon，不能排除旧 App。当前工程没有跨版本单实例或阻重启协议；同一 macOS 用户的普通目录权限也不能按 App 版本区分。因此“此刻没有旧进程”、新版 READY 回应或只持 `store.lock` 都不能授权自动搬迁。

可执行的首个入口应是**受控升级的离线维护操作**，而非普通启动或后台轮询。升级器或维护助手必须证明以下条件；不能证明就保持旧根原件和现有失败关闭状态：

1. 停用旧 App 的登录启动，等待旧 App 与旧 Daemon 退出；受管理的旧 App 包、Daemon 路径及开发覆盖路径已原位替换或移除，不能由登录项或升级器再拉起。核对当前同用户的 AgRoom 与 Daemon 进程的可执行路径和版本；未知副本、无法核实的进程或只能获得瞬时进程列表而无阻重启控制时拒绝迁移。用户确认或进程列表本身不能替代这一证明。
2. 核对本次迁移仅使用 AgRoom 的应用支持目录，并检查其中旧根凭证与新分区目录有无冲突。
3. 新 App 已停止新发送、交接、任务监督、会话恢复写入及本地在途运行。维护者先非阻塞取得并核对旧根 `daemon.lock` 的固定 inode；旧 Daemon 正运行就延后。所有文件变更依 `daemon.lock → store.lock` 顺序进行，`store.lock` 只保护短文件事务；数据库探针在锁外使用已健康挂载的目标空间库，锁内不跨 `await`。发布前重核原始字节、状态、恢复代际和目标冲突，任何变化保留原件并转人工。

当前仓库尚无可证明“旧版本不能重新启动”的安装器或维护助手，也没有已接入运行扫描的持久 marker/manifest。故上述条件目前是**未满足的启用门禁**；只读盘点和数据库预检候选不授予迁移、删除或续跑权限。将来 marker 必须在首次改变旧证据前持久落盘；重启先按 manifest 对账，不能因目标副本看似完整就删除旧副本或重放工具。

### 版本化根原子切换候选（未实施）

若需要应用内阻止**已知旧二进制**重新向旧根新增文件，可评估预建新布局和旧写者无法写入的 fence，再以同卷 `renameatx_np(RENAME_SWAP)` 原子交换根目录，旧根成为受限 archive，新版 Store 从新根启动。该候选不等于现有能力：切换改变 `daemon.lock` inode，须分别处理切换前旧 Daemon 持锁、切换中已打开的目录/文件描述符、切换后新版 Daemon 接力；还要迁走现有两个空间目录、阻止旧活跃任务丢失，并让 archive 的未知证据持续阻挡。目标文件系统的原子交换支持、`0555`/immutable fence 对受审计旧二进制的效果、同用户清除标志的边界及各中断点均须先验证。任一条件不成立就不切换，也不回退到非原子重命名或仅凭进程检查执行迁移。

纯读预检不得调用 `SpaceStore.queue(for:)`：未挂载时它会打开或初始化空间库，可能执行迁移及建表。预检只接受调用方提供的、已健康且绑定**目标空间**的单库只读探针结果；目标空间从 owner 与正文一致的可信身份确定，不为预检读取另一空间库，两空间相同 UUID 仍是独立数据。预检结果不授予搬迁或删除权限。真正执行前必须在受控升级窗口证明旧版写者已停、重新读取源文件并核对原始摘要及状态、重新核对所属空间库和持久 manifest；不能把异时或误配的探针结果当成当前授权。

## 验收矩阵

| 场景 | 必须验证的结果 |
|---|---|
| 两空间各有快照、owner、journal 和隔离文件，甚至使用相同运行及会话测试 UUID | 两个 `(space, id)` 独立执行与收尾；文件各在所属目录，空间限定 API 只返回本空间数据；相同会话 ID 不造成跨空间阻塞或删除。 |
| `personal/` 路径中的记录或 owner 声称 `work`，或两者会话/消息 ID 不同 | 两边都不执行、不跨目录挪动；原文件保留，归属无法确认时人工恢复。 |
| owner 已落盘但 record 写失败；record/owner/journal 损坏或不可读 | 不释放执行权给第二进程，不把目录当空任务；保留原文件和会话阻塞。 |
| 同一 `(space, id)` 同时在旧根和对应空间新目录；另有相同 ID 只分别位于 personal/work | 前者在任何工具前判重、停止执行并保留现场；后者作为两个独立运行正常处理。 |
| 活跃旧运行与新运行并存；状态推进、journal、`committing` 写回及删除 | 旧运行始终在旧来源完成，新运行始终在指定空间；两者最终都只执行/提交一次。 |
| 升级时旧 Daemon 持锁，不理解新布局；新 Daemon 崩溃重启 | 新 App 不把仅新 Daemon 可见的记录交给旧进程；新 Daemon 重启能扫描两空间和旧根。 |
| 迁移在复制 owner、正文、journal、隔离文件或删除旧副本时逐点崩溃 | 原始证据始终可找回；双份/半份失败关闭；不因修复布局而重放未知写入。 |
| 旧损坏文件无可信 owner，及用户明确放弃 | 不猜空间；全局阻塞直到人工处理，放弃只解除相应续跑阻挡、不执行工具；留在 `abandoned/` 的原始字节仍须单独归属或明确处置。 |
| 全局根目录与日志审计 | 新写入后根目录无新增会话内容、工具回执或身份 sidecar；旧 `daemon.log`、孤儿 journal、迁移临时文件及 `abandoned/` 均递归盘点；彻底迁移前明确标识 legacy 残留。 |
