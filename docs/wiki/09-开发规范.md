# 开发规范

这些规则适用于阿吉屋（AgRoom）的日常开发。项目特有架构约束同时受 [AI Coding 指引](00-AI-Coding指引.md) 和对应领域文档约束。

## 命名和结构

- 名称表达领域意图，避免 `temp`、`data2`、`handlerNew` 等无语义名字。
- Swift 类型使用 PascalCase，成员使用 camelCase；布尔值采用 `is`、`has`、`should` 等问句形式。
- 一个概念使用一套稳定术语；改名时清理旧别名和调用点。
- 函数保持单一职责，优先 guard 和早返回减少嵌套。
- 参数过多时使用配置结构；重复逻辑达到稳定模式后再抽象。
- 公共接口注释说明输入约束、失败语义和线程要求，代码注释重点解释“为什么”。

## 错误处理

- 可恢复错误在当前层处理，不可恢复错误向上抛出。
- 用户可见错误转换为清楚的原因和下一步动作。
- 数据写入、网络、资源加载、进程和恢复路径不得静默吞错。
- `try?` 或空 catch 只用于失败确实无影响的清理，并写明原因。
- 不用 nil、空串或负数混合表达成功与失败；使用明确结果或错误类型。
- 重试设置上限与退避，仅用于可安全重试的操作。

## 日志

- 生产代码统一使用 `HubLogger`，禁止 `print` 和分散的临时日志通道。
- debug 用于诊断细节，info 用于状态变化，warning 用于可自愈异常，error 用于需要关注的失败。
- 日志包含可定位的对象和步骤，但不记录密钥、token、口令或未脱敏用户内容。
- 本机绝对路径、附件/技能/通知/提醒名称、模型原文和外部服务错误说明都属于用户内容；日志只保留稳定阶段、必要计数及 `HubLogger.safeErrorSummary` 生成的错误类型与码。用户可见错误仍在 UI 层单独转换为可操作的三语说明。
- 同一事件使用稳定短语，避免高频循环大量记录。

## 并发

- 每个可变状态明确属于某个 actor、锁或串行执行器。
- UI 状态只在主 actor 更新；跨边界值满足 Sendable 或有显式同步。
- 锁临界区保持短小，锁内不执行文件、网络、数据库、回调或 await。
- 长任务支持取消并定期检查，退出时释放资源且不留下半成品。
- “不存在则创建”的惰性初始化处理并发首次访问。
- 异步回调携带稳定运行身份，旧任务不能覆盖新任务。

## 数据与文件

- 明确单一权威数据源，缓存只保存可重新生成的派生数据。
- 多字段或多表一致性变更使用事务。
- 文件写入使用临时文件和原子替换。
- 格式变更向后兼容；确认已有数据完成迁移后才删除兼容读取。
- 删除、覆盖和恢复遵循先可逆后不可逆，并保留失败时的恢复路径。
- 启动扫描、恢复与运行期写入需要串行或互斥，避免把中间态当成完成状态。

## 安全和隐私

- 所有外部输入在使用前验证：用户输入、模型输出、文件、网页、URL、SQL、脚本和反序列化数据。
- 文件路径标准化后再检查允许根；拒绝目录穿越和符号链接逃逸。
- 密钥只存 Keychain，远程请求只使用安全端点。
- `EndpointSafety` 的「仅 HTTPS」规则面向 HTTP 端点，不覆盖邮件协议。邮箱走 IMAP / SMTP 时同样必须使用用户显式选择的 TLS 或 STARTTLS 配置，不隐式降级到明文；凭据只在认证阶段发送。
- SQL 使用参数绑定；动态标识符严格白名单。
- Shell 参数使用结构化传递，不拼接未转义文本。
- 错误和日志避免暴露本地绝对路径、密钥或隐私正文给不需要的接收方。
- 新依赖说明用途、许可证和维护状态，并锁定版本。

## UI 和本地化

- 用户文案同步维护 en、zh-Hans、zh-Hant；不要在视图中散落硬编码文本。
- 模型提示词、协议字段和工具定义与 UI 文案分开管理。
- 错误、加载、空状态、禁用原因和进度都有可理解反馈。
- 支持键盘操作和辅助功能标签；不能只通过颜色表达状态。
- 大列表、图片、Markdown 和 WebView 避免在主线程做无界工作。

## API 与依赖

- 先明确接口契约，再写实现；公共行为变化同步更新调用方、测试和 Wiki。
- Core 不依赖 UI，服务不反向依赖具体工具。
- 不为单个调用引入全局单例或隐藏状态。
- 新依赖必须带来明确收益；能用系统框架和现有依赖解决时不增加包。

## 测试原则

- 测试外部可观察行为和关键不变量，不复制私有实现。
- 错误、取消、权限拒绝、磁盘失败、旧数据和并发交错与成功路径同等重要。
- 时间、网络、文件位置和随机性通过依赖注入保持确定性。
- 空间功能至少验证两个空间使用相同 ID 或相似内容时仍不串写。
- 修复缺陷时优先添加能在旧实现失败的回归测试。

## 评审与文档

- 一个变更围绕一个清楚的行为目标，说明改了什么、为什么和如何验证。
- 不提交注释掉的代码、临时产物、用户状态或调试输出。
- TODO/FIXME 写清原因和移除条件。
- Wiki 记录稳定契约和决策，不复制源码清单、行号、测试数量、版本号或一次性审查过程。
- 发现 Wiki 过期时在当前变更中修正；历史由 Git 保存。
