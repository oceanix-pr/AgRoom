# 构建、运行与测试

## 环境

- 应用部署目标是 macOS 15。源码使用 macOS 26 SDK 的 Speech API，锁定依赖要求 Swift 6.2 或更新工具链。XcodeGen 的 `xcodeVersion` 描述生成工程的格式。实际构建需要同时满足 SDK 和 Swift 工具版本。
- 命令行检查应使用完整 Xcode 工具链。仅安装 Command Line Tools 时，SwiftUI 宏插件等能力可能不可用。
- GRDB 使用官方 Swift Package。两份锁文件均记录上游标签的提交。开发机镜像中自行删减子模块产生的提交只能在该镜像内检出。发布前用独立的 SwiftPM 配置目录从公开 URL 验证两份锁文件。
- 邮件协议栈依赖 `MailFoundation`（IMAP / SMTP）与 `MimeFoundation`（MIME 解析）。`MailFoundation` 使用 `AgRoom/vendor/MailFoundation` 中的固定源码副本，来源与升级步骤见该目录的 `AGROOM-PATCH.md`；`MimeFoundation` 在应用清单、固定副本清单和 XcodeGen 中使用同一 revision，避免解析工程时更新分支。升级时同步修改这三处声明及两份 `Package.resolved`，并在 SPM 与 Xcode 两条路径都验证。
- IMAP / SMTP 的底层连接都使用 Network.framework，按账号配置使用 TLS 或 STARTTLS。固定副本在包清单中移除 Apple 平台未使用的 OpenSSL system-library target，避免 SwiftPM / Xcode 探测 pkg-config 并提示安装 OpenSSL；无需安装 OpenSSL，也不通过屏蔽警告解决。源码仅清理 actor 内两处冗余 `await`，邮件协议行为保持上游实现。
- MySQL 的 vendored `swift-nio-ssl` 在 NIOSSL target 开启 `CheckImplementationOnly`。`ByteBufferBIO` 用不透明指针保存 BIO，在调用 C 接口时还原指针类型，使 Swift 6.3 也能检查模块边界。BoringSSL 的上游整型转换告警仅在 `CNIOBoringSSL` target 配置中抑制 `shorten-64-to-32`。本地静态分析兼容补丁清理未使用赋值、显式保护 PKCS#12 空输入的取模条件，并初始化 TLS 解密 nonce 缓冲区；不修改整型转换或密码算法，也不关闭静态分析检查器和应用代码告警。补丁、标准签名向量及空口令回归记录在该依赖的 `AGROOM-PROVENANCE.md` 与 `AGROOM-ANALYZER.patch`，升级时先复现诊断，再逐项复核。

## 双构建配置

项目同时维护两套入口：

| 文件 | 用途 |
|---|---|
| `Package.swift` | 命令行构建、测试、依赖解析和产品定义 |
| `project.yml` | XcodeGen 配置，是 Xcode target、资源、签名和 scheme 的事实源 |

两者的 target、源码目录和依赖必须同步，第三方依赖还要同时出现在 `Package.swift` 的 `dependencies` / target 依赖与 `project.yml` 的 `packages` / target `dependencies` 中；只改一边会让 SPM 能编译而 Xcode 报「No such module」。`AgRoom.xcodeproj` 是生成产物；需要调整工程结构时修改 `project.yml`，再运行 `xcodegen generate`，不要只手改 pbxproj。

## 常用命令

在应用工程目录运行：

```bash
cd AgRoom
```

核心构建与测试：

```bash
env DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build
env DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test
```

笔记本地推理依赖 WhisperKit 和静态 sherpa-onnx/ONNX，两个清单必须同步，许可证位于 App 的 `Notices`。上游静态 ONNX 产物采用 framework 容器；新版 SwiftBuild 默认引擎可能错误嵌入该静态容器并在测试包签名时报错。遇到该问题使用相同工具链的原生 SwiftPM 引擎：

```bash
env DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test --build-system native --force-resolved-versions --no-parallel
```

Xcode 工程对静态 sherpa 产品显式关闭嵌入，只链接到 Core；不要用动态库签名脚本改写静态库，也不要通过跳过 App 签名掩盖构建问题。核心回归之外仍需构建/签名 App 并检查其实际嵌套产物。

重新生成 Xcode 工程：

```bash
xcodegen generate
```

验证 App target：

```bash
xcodebuild \
  -project AgRoom.xcodeproj \
  -scheme AgRoom \
  -configuration Debug \
  -destination 'platform=macOS' \
  build
```

如果受限环境不能写默认缓存，可把 scratch 和 cache 指向允许写入的临时目录；这属于执行环境设置，不应固化为产品配置。

## Xcode 依赖解析失败

GRDB 的 Swift Package 通过 `GRDBSQLite` 链接系统 SQLite。上游同一仓库还为单独的自编译 SQLite 工程登记了 `SQLiteCustom/src` 子模块。如果日志明确显示只有 `swiftlyfalling/SQLiteLib` 检出超时，可以在应用工程目录仅为这一条解析命令跳过它。Git 的设置随命令结束失效，GRDB 仍从官方提交检出。

```sh
env GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=submodule.SQLiteCustom/src.update GIT_CONFIG_VALUE_0=none \
  swift package resolve --force-resolved-versions
```

多个 target 同时出现 `Missing package product` 时，先查看 Report Navigator 中最新的 Package 解析日志。远端拉取失败或 `SourcePackages/repositories` 缺失会使整张包图不可用，连带影响远程包和本地固定副本的产品引用。

重建依赖缓存前，先等待当前解析结束并关闭该工程窗口，避免 Xcode 在解析期间继续引用已移除的 checkout。然后在应用工程目录运行正常解析命令。

```bash
env DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  xcodebuild -resolvePackageDependencies \
  -project AgRoom.xcodeproj -scheme AgRoom
```

解析成功后重新打开同一路径的 `AgRoom.xcodeproj`，从 Xcode 执行 AgRoom 构建，确认 IDE 已刷新包图。

## 何时运行哪些检查

| 改动 | 最低验证 |
|---|---|
| Core 纯逻辑、模型、服务、调度 | 相关测试 + `swift test` |
| UI 逻辑或 BrowserTools | `swift test`，并构建 AgRoom |
| 新增、删除或移动 Swift 文件 | `xcodegen generate` 后同时验证 SPM 与 Xcode |
| `project.yml`、资源、Info.plist、entitlements | 重新生成工程并运行 Xcode 构建 |
| 数据库 schema、备份、恢复 | 旧数据迁移、失败回滚和跨重启测试 |
| 邮箱同步、协议适配、凭据 | 用内存 mock 客户端跑同步与写操作测试（增量游标、失败不改本地、发信落副本）；适配器级用内存字节通道回放 IMAP 会话，检查最终发出的命令（路径只编码一次）与错误分类 + `swift test` |
| 并发、取消、daemon | 可控延迟和交错顺序回归测试 |

完整回归可使用 `swift test --no-parallel`，避免大量同时启动的测试使短期限夹具因调度拥堵误报；各测试内部的并发、交错和取消验证仍照常执行。运行期间保持机器唤醒，系统休眠造成的墙钟跳变不能作为产品超时行为的证据。

GitHub Actions 在两台 macOS 托管机上分别编译并运行串行测试。`--filter ProductTaskCenterHostTests` 运行任务中心的原生窗口交互，`--skip ProductTaskCenterHostTests` 运行其余套件。两组均须报告完成并通过。测试通过伪终端实时输出进度，连续两分钟没有输出时会记录测试进程的调用栈。窗口点击夹具先命中测试窗口内的真实控件，分段选择器触发对应选项的原生动作，自定义视图接收按下和松开事件。

## 运行前置条件

首次启动需要配置可用的 LLM Provider。API Key 写入 Keychain；端点经过 HTTPS 安全检查。麦克风、提醒事项、通知等系统能力由 macOS 在首次使用时请求权限。

SPM 的 executable 运行不等于完整签名的 App bundle，涉及 entitlements、Keychain ACL、TCC 或嵌入 Daemon 的行为要在 Xcode 构建中验证。

## 签名与 Daemon

App 使用稳定的开发签名和 Hardened Runtime。开发者在 `Config/Signing.local.xcconfig` 设置自己的 `DEVELOPMENT_TEAM`，或向 `xcodebuild` 传入 `DEVELOPMENT_TEAM=自己的团队ID`。共享的 `Config/Signing.xcconfig` 同时用于 Debug 和 Release，两个空间的执行器继承同一团队。Bundle ID、entitlements 和嵌入方式由 `project.yml` 定义。临时 ad-hoc 签名会改变代码身份，可能导致 Keychain ACL 反复提示，缺少团队身份的执行器也无法通过运行时校验。

`AgRoomDaemon` 作为工具 target 嵌入 App，不应作为独立安装产品进入归档。修改 daemon target 后检查 App 包内位置、签名和启动路径。

Daemon 空间分区与交接改动须使用临时 Application Support 目录验证：新 `personal/`、`work/` 分别存快照、owner、journal 和隔离证据；旧根记录原地收尾；同空间双份与无法归属证据阻止自动执行，同空间重复在任务中心只显示警示，不开放共享根文件；跨空间同 UUID 不相互删除。故障注入覆盖 owner 已写但正文失败、日志/快照损坏、交接记录状态不明、旧 Daemon 持锁时新进程 READY、READY 后新进程退出、重复领取及最终写回交错。READY 仅证明待命进程完成一次握手，不能代替真正接管和结果落库的端到端验证。重启确认/提问卡还须验证只读核对、结束等待失败保留卡片、无自动模型请求与无旧批准重用。涉及真实进程、签名、TCC 或系统选择器的场景须在完整 App 环境复核；临时夹具通过不等于这些现场路径已通过。

Store 与原生宿主夹具可注入临时根，验证空间页读取不移动其他空间的损坏凭证、原件仍可作为未决证据发现、跨路径身份冲突在冷启动发送前同步阻挡。实际 `DaemonMain` 使用 AgRoom 的默认 Application Support 根；仅替换 daemon 可执行文件路径不能隔离数据。真实 relay 进程故障注入须使用独立 macOS 测试用户或专门的无生产数据测试装配入口，不能直接拿当前用户资料做 smoke。

旧根迁移盘点使用独立的 `DaemonLegacyInventory` 和合成临时目录：递归覆盖旧运行、owner、日志、孤儿 journal、人工放弃目录、链接及未知文件；盘点不得进入 `personal/` 或 `work/`，不得移动原件或把正文写入日志。owner、正文与 journal 相符只算文件级佐证，迁移前还须核对空间数据库、进程静止、目标冲突及中断恢复。

迁移预检使用两份独立临时空间库验证隔离，但每次只向计划器注入目标空间的单库读服务结果：目标库的会话、唯一助手消息、任务运行身份、恢复代际与终态必须精确一致；损坏消息、缺库、未决状态或探针与文件身份错配都延后。两空间相同 UUID 是合法独立记录，不能要求读取对侧数据库才能给目标空间预检结论。把盘点时为活跃的正文在输入中伪装为完成态，或把另一记录的探针结果套用过来，都不能产生候选。预检不移动文件，也不能代替发布前的重新读取、摘要核对和旧版进程停机证明。

新版 Store 的 `store.lock` 回归还须验证：锁 inode 被替换或持锁超时会失败关闭；日志目录/文件及空间目录、隔离目录被符号链接替换时不沿链接写入或删除；`work/` 指向 `personal/` 时，删除 work 凭证不得改变 personal 的正文和 owner 字节。人工放弃按 `daemon.lock` 再 `store.lock` 取锁，跨数据库等待前释放，返回后重新核对来源与摘要。旧版本不识别新锁，以上宿主夹具不能代替升级窗口和真实双进程故障注入。

独立脚本执行器由 `SandboxRunner` target 模板生成 `AgRoomRunnerPersonal` 与 `AgRoomRunnerWork`，身份分别为 `com.agroom.runner.personal`、`com.agroom.runner.work`，位于主 App 的 `Contents/Helpers`。本空间的 Shell、Python/技能、环境变更和固定包解析共用对应执行器。执行器只依赖静态 `AgRoomScriptIPC`，不链接 Core/UI，不声明网络、主 App 的提醒事项、Keychain 或共享容器权限。`SpaceRunner.entitlements` 仅对固定 `Documents/AgRoom/python-runtime/` 与当前执行器空间的 `python/<space>/venv/` 增加只读静态路径权限，补足动态书签不授予的可执行映射权限。路径由 `AGROOM_RUNNER_SPACE` 在签名时展开，宿主核对完整白名单，另一空间环境不在其中。包下载由 Core 的受限 HTTP 传输完成，每次传输单独核对地址、跳转与预算。Release 执行器关闭基础调试权限注入，宿主在加载时拒绝可调试的 Release 助手。执行器不能使用 `com.apple.security.inherit`，也不能用 `codesign --deep` 重签覆盖独立权限。原生 Copy Files 阶段保留各执行器已有签名，不执行 CodeSignOnCopy 或移除头文件；`verify-script-runners.sh` 逐个只读验证最终副本，主 App 最终签名包含嵌套产物。

脚本沙箱保持开启。复制与签名由 Xcode 原生构建阶段处理，校验脚本只声明最终 App 包内的递归输入，不写目录输出。[Swift Build 的脚本沙盒实现](https://github.com/swiftlang/swift-build/blob/main/Sources/SWBTaskConstruction/TaskProducerSandboxing.swift) 对普通输出路径使用精确匹配，单独声明 `Helpers` 目录并不能授权创建其中的 App 和文件。IPC 静态库仅供 Swift 使用，关闭 ObjC 兼容头安装；[XcodeGen 的生成条件](https://github.com/yonaskolb/XcodeGen/blob/2.46.0/Sources/XcodeGenKit/PBXProjGenerator.swift#L1055) 会据此省略无用的头复制脚本，避免 `ditto` 在未声明的头目录中创建临时文件。

Archive 时 `SKIP_INSTALL=YES` 的执行器实际位于 `UninstalledProducts`，`BUILT_PRODUCTS_DIR` 下只有符号链接。原生 Copy Files 处理此归档布局，后续校验直接读取主 App `Helpers` 中的真实副本，避免沙盒只授权符号链接路径、却拒绝读取实际 App 及其扩展属性。排查此类错误应核对构建阶段与实际路径，不要清除 quarantine 属性或关闭脚本沙盒。

本机开发使用现有 Apple Development 身份即可；对外发布时主 App、Daemon 与全部执行器应保持同一团队的适当分发签名，随后公证。SPM 只编译共享源与执行器程序，不生成具有独立沙箱身份的签名 App；空间内脚本执行需要 Xcode 产物，不能降级到 SPM 裸可执行文件。

应用 Python 只使用 `~/Documents/AgRoom/python-runtime/bin/python3` 和 `~/Documents/AgRoom/python/<space>/venv`，不借用系统或开发工具中的解释器，也不复用旧 Application Support 环境。缺失时由用户在 Python 环境页主动下载安装。专用运行时的兼容回归在未安装时明确跳过，不自动选择其他本机解释器。独立执行器的隔离、文件流和成果回执另有显式注入的 Xcode Python 测试夹具；它只操作临时合成数据，不初始化用户空间环境，不代表已验证专用运行时或用户包。两种回归分别报告，生产装配不接受这项注入。

Shell 与 Python 使用相同执行源码、协议和本空间的统一离线容器。协议升级时必须同步重建全部执行器，版本不匹配拒绝执行。显式文件流在授权完成后接入 stdin/stdout/stderr，控制请求始终使用启动时的匿名 stdin，并在 exec 前关闭；未声明数据输入时 stdin 为 `/dev/null`。输出在单次私有目录暂存，文件大小硬限额在执行器中生效，发布由宿主的路径检查与条件原子写负责。执行器 target 依赖通过原生 Copy Files 显式嵌入 `Contents/Helpers`，不复制到 Resources，避免出现第二份 App。

## 内置知识推理程序

知识检索入口 `llama-embedding`、本地意图入口 `llama-intent` 与共用 llama.cpp 动态库位于 App 源目录的 `EmbeddingRuntime`，包含 Apple Silicon 与 Intel 两套运行库，源版本和官方压缩包校验值记录于 `provenance.json`。开发者更新/重建时运行 `scripts/prepare-knowledge-runtime.py`，该脚本验证官方包摘要，以同版本头文件编译两个入口并只收集递归依赖；知识入口检查空上下文，意图入口限制输入、上下文与生成量并约束 JSON 输出，两个入口都在父进程退出时清理。第三方许可证一并保留。

SPM 将该目录作为 App 的显式资源复制；Xcode 原生 Copy Files 阶段按架构将入口与动态库复制到 App 的 `Contents/Helpers/EmbeddingRuntime`，逐项启用 CodeSignOnCopy，以 App 同一身份签名；许可证与来源记录另行复制到 `Contents/Resources/EmbeddingRuntimeNotices`。`scripts/verify-knowledge-runtime.sh` 以递归只读输入校验最终代码签名。更新运行库文件后必须重新生成工程，确保原生复制阶段包含新的文件集合。变更后必须构建完整 App，并验证嵌套签名和 App 包内程序实际推理。模型权重不属于任何 target 资源或复制阶段，默认从用户 Documents 目录读取，可在设置中更改路径。

真实模型测试可通过 `AGROOM_TEST_EMBEDDING_MODEL` 指向外置 GGUF 文件启用；普通回归使用确定性假向量验证独立语义召回、空间隔离、修改/删除失效、并发编辑和取消。

意图路由回归位于 `LocalIntentRoutingTests`，并复用协议夹具验证延迟工具的原有确认与签名恢复。自动工作流回归同时覆盖跨领域选择、短续问、保守修复兜底、按需激活的编程记账、硬构建确认、快照恢复和共用模型偏好的旧记录兼容。真实推理需同时设置 `AGROOM_TEST_INTENT_MODEL` 为外置 LFM GGUF、`AGROOM_TEST_INTENT_RUNTIME` 为当前架构的 `llama-intent` 绝对路径；可用 `AGROOM_INTENT_EVAL_REPORT` 保存合成样本分类、耗时与实际生产定义的本地 Token 估算。测试不会连接云端模型或执行邮件等业务工具。小规模合成检查不证明真实业务准确率、整体对话节省比例或远端费用。

## 邮箱 TLS 联调

普通回归使用内存字节流验证 SMTPS 的证书校验、TLS 先于 SMTP 命令、握手失败不降级、静默欢迎信息/EHLO 的主动断链，以及端口与加密方式预检。可通过 `AGROOM_TEST_SMTP_HOST` 显式启用真实 SMTP 465 联调；该用例只建立 TLS、读取欢迎信息和发送 EHLO，不使用账号密码、不投递邮件。第三方源码无需修改，隐式 TLS 包装保留在唯一协议适配器内。

## Markdown 离线渲染资源

公式和图表引擎位于 UI 的 `Resources/Markdown`，固定发布包来源、校验值、许可证和字体内嵌方式记录在同目录 `VENDOR.md`。SPM 与 Xcode 均将其作为 UI 资源包含；更新时同时验证两条构建路径，运行时不得改为 CDN 加载或复用用户浏览器会话。

Markdown 富内容测试直接使用随包引擎生成深浅色公式与图表；复杂多图用例必须经过视图模型的实际像素总预算，并从空模型挂载 SwiftUI 宿主开始加载，避免后端单测通过而界面拒绝结果。图片网络测试仅使用本机回环 HTTP 夹具，不访问外部图片服务。设置 `AGROOM_MARKDOWN_SNAPSHOT_DIR` 为已存在的临时目录可导出原生宿主和离线输出预览，供窄宽布局、附件基线和块级高度视觉复核。

## 可选的真实模型应用流程验证

`NativeAppScriptReviewTests` 使用临时应用、合成签名密钥和审核回执，验证持久批准、伪造标记与摘要、凭证链接、原始定义字节变更、环境变更、跨空间/安装复用、更新与恢复失效，以及审核期间定义变更。签名执行器回归另验证新输入重复运行免确认、重建服务复用批准、准备后凭证被改动时停止，并重新审核。测试不访问真实 Keychain 或外部模型。

`NativeAppScriptTests` 的普通回归覆盖 DSL 兼容、完整记录快照、附件隔离、结构化结果和恶意产物；设置 `AGROOM_TEST_SANDBOX_APP` 指向完整签名 App 后，还验证真实 Python 函数的批准/拒绝、结果回填、附件读取、应用目录拒绝、日志截断不影响结果、产物另行保存、缺依赖、超时、取消与更新后旧审批失效。它使用临时合成工作区与注入的签名执行器，不修改用户的空间 Python 包或业务记录。

常规测试不调用外部模型。显式设置 `AGROOM_TEST_NATIVE_APP_PROVIDER=1` 并筛选 `NativeAppProviderFlowTests` 才运行配置模型的合成案例；可用 `AGROOM_APP_FLOW_ARTIFACTS` 指定临时产物目录。用例只读全局提供者配置，通过现有 Keychain API 读密钥，不导出凭据；系统可能要求授权测试进程读取；模型执行超时从授权完成后开始计算，人工等待不消耗生成时限。定义、待安装草稿、用量账本和应用安装都位于临时目录，预览与打开使用真实 SwiftUI/AppKit 渲染及生产安装动作；产出定义、预览图、窗口图和简要结果。该测试不能替代常规确定性测试，也不能由定时任务自动启用。

已有模型生成的定义可用 `AGROOM_TEST_NATIVE_APP_DEFINITION` 指定，并筛选 `generatedDefinitionInteractions` 独立重放原生运行验证。它不调用模型或读取 Keychain，在临时安装中验证预览、保存前审批、拒绝不写入、记录重开与同 ID 编辑、删除审批及独立窗口；产出含窗口背景的截图与运行结果，避免透明截图掩盖文本。

## 知识整理与用量回归

用量页的日期边界、缺失计数、同名模型来源及过滤后分页由 `UsageDashboardQueryTests` 验证。`UsageDashboardRenderingTests` 使用合成账本渲染三语、深浅色与较大界面字号的窄宽布局；设置 `AGROOM_USAGE_SNAPSHOT_DIR` 为已存在的临时目录可导出预览，不读取真实空间业务数据。

本地小应用动作回归覆盖全按键计算、十进制精度、运算优先级、错误不覆盖结果、无 Python 的草稿准备，以及 Schema 章节与长范例的完整分页。签名执行器回归另验证本机已安装专用 Python 运行时的跨进程 stale 书签刷新和同路径对象替换拒绝；不自动安装运行时，不扩大聊天工作区权限。

稳定性回归使用合成空间数据库与临时目录，覆盖恢复维护期间的竞争写、恢复后旧快照及守护进程写回、损坏会话拒绝导出、分页尾部保存、账号删除保护、排队取消、团队运行时限、图片降级次数、SSE 与图像输入边界、独立技能日志实例及编辑草稿恢复。知识检索另验证多批游标与范围内向量读取量；富文本测试验证未变化块复用及输出一致性。测试不访问用户邮箱、真实空间业务数据或外部模型。

首次成果回归使用独立空间库、工作区、偏好存储和注入的本地模型传输，不接触真实账号或启动浏览器、守护进程与自动定时。原生测试操作引导连接测试与开始按钮，经过真实 Provider 协议、调度引擎、文件工具和审批卡，核对批准前无写入、批准后有实际成果，再重建视图模型、删除原文件、打开保留副本并确认成果有用。连接回调交错、设置恢复、来源失效、邮箱本地覆盖和保存失败另有故障回归。注入点属于 UI 组合层；正式应用继续使用 `EngineAssembly` 和原有权限策略。该示例链不替代外部文件选择器以及资料对比、邮件摘要的完整交互验收。

`KnowledgeImportLifecycleTests` 使用临时文件与独立空间库，验证真实图片和扫描 PDF 的本机 Vision OCR、编码与大小边界、同批次重复、失败修复重试、立即取消与暂停提取取消、保存前来源变化、后来编辑冲突、原子回执、幂等提交，以及来源/版本/记录的备份恢复和回退。恢复后的来源检查必须先返回重新选择，不读取旧路径。原生窗口测试从导入按钮检查正文与默认跳过、实际保存、来源丢失后重新选择并排预览、更新与旧版本阅读；文件选择器边界注入临时 URL，之后走真实提取与保存。系统文件选择器另在独立签名 App 宿主下完成手工验收：多选确认、取消、来源丢失后的重新选择更新、旧版本阅读，以及编辑冲突的默认保留、取消确认和明确替换后保留手工正文。此宿主只验证当前 App 的文件访问策略，不代替独立沙盒执行器的目录授权测试。
