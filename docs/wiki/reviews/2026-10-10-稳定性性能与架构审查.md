审查日期：2026-10-10。对象为本次审查时的工作区源码，包含尚未提交的改动。本文件是一次审查记录；修复时仍需重新核对实现。本文给出修改方案，不代表产品代码已经完成修复。

## 结论与证据边界

当前工程的不签名 Xcode Debug App 构建通过；Swift 测试曾全量通过，但正式测试复跑捕获了 JobHistory 的完成/落盘竞态，定向复查又通过。还不能据此认定异常恢复、跨空间后台处理和不可逆副作用已经可靠。最值得先解决的是原数据保护、空间绑定和后台恢复协议；性能优化随后围绕数据库候选检索与主线程文件 I/O 展开。

证据分为三档：

- **已复现**：用真实服务、内存数据库、临时文件或 URLProtocol 替身验证到了当前错误行为。临时探针中的“通过”表示错误行为得到证实，并非修复后的验收通过。
- **源码确认**：调用链和条件可以直接从实现确定，尚未执行完整 UI 或真实服务器复现。
- **待实测/待决策**：存在明确机制或产品取舍，但尚无发生频率、生产数据规模或真实资源曲线。

没有进行真实邮箱投递、真实 LLM 付费请求、生产库恢复、系统权限交互或签名 App 的长时间运行。本文不声称已经测得线上崩溃率、整体安全等级或长期内存泄漏。

## A01：空间归属必须贯穿后台后处理

**位置**：`RootView.swift` 的 `ChatViewModelCache`；`ChatView.swift` 的 `autoDistillMemoriesIfNeeded`、`recordAutoReview`、`reloadSkillAliasCache`、草稿读写；`Hub.swift` 的 `makeMemoryService` / `makeSkillStore`。

聊天模型按空间缓存，切到另一空间后旧模型仍可完成运行。引擎主路径显式传 `space`，但开启自动记忆且达到提炼轮次后，提炼流程在等待 Provider 后调用无空间参数的 `hub.makeMemoryService()`，该方法使用此时的 `currentQueue`。因此 A 空间对话完成后切到 B，可把 A 的提炼内容写到 B。审核记录与技能别名也从当前空间取目录，可能写错审计归属或显示另一空间信息。

草稿全部写入同一个 `agroom.chat.drafts` UserDefaults 键，两空间共享完整字典。这已经不符合隐私内容物理隔离的约束；两个缓存模型还可能用旧字典互相覆盖更新。

**修改说明**：

1. 为非邮箱空间服务提供显式 `for space:` 组合入口；后台任务只使用模型或运行冻结的空间，不再读取可变 `current`。保持 Hub 现取现建。
2. 把自动提炼、审核记录和技能快照依赖在任务发起时固定到空间；为审核记录带上可校验的空间/运行身份。
3. 草稿进入空间数据库或空间目录；迁移旧字典时按会话所属空间分流，归属未知项保留在隔离恢复区，不猜测。

**验收**：A 完成前切到 B；Provider 返回期间切空间；同 UUID 的两空间会话；A/B 交替改草稿并重启。数据库、技能目录、审核文件及草稿都只发生本空间变更。

## A02：备份回滚不是恢复原状态

**位置**：`BackupService.restore` / `rollback`，`SessionService.save`，`MemoryService.save`。

恢复直接 upsert 会话与记忆，记录的是导入后的对象；失败回滚则对这些 ID 执行删除，没有保存覆盖前值。同 ID 恢复时，删掉的是原本已存在的记录。覆盖技能只记录在 `overwrittenSkills`，没有进入自动回滚列表；回滚自身失败也仅记日志，却始终返回“原数据未变”的 `rolledBack` 错误。

**复现**：目标库先存旧会话，备份包含同 ID 新会话和一条记忆；用 SQLite trigger 让记忆写入失败。恢复抛出 `rolledBack`，目标库的旧会话实际已经不存在。

**修改说明**：

1. 数据库段在同一事务中提交，或先记录完整 before-image，明确区分新增与覆盖；失败时恢复旧值，只删除本次新增项。
2. 文件段先暂存，保存可校验的恢复点，再原子替换；覆盖技能必须进入恢复计划。
3. 数据库与文件之间建立持久恢复记录，支持进程退出后继续回滚。恢复期间限制同空间的竞争写入。
4. 错误区分“未开始写入”“已完整回滚”“回滚不完整”，最后一种必须保留恢复材料并展示处置入口。

**验收**：同 ID 会话/记忆冲突、第二段失败、技能覆盖后失败、回滚写失败、恢复中杀进程。逐项比较恢复前后内容，而非只检查抛错或条数。

## A03：损坏消息不能被伪装成正常的短会话

**位置**：`SessionService.loadMessages` / `save`，`ChatViewModel` 的消息加载与持久化路径。

单条 payload 解码失败会被 `continue` 跳过；旧整包解码失败返回空数组。上层得到正常数组，无法知道内容缺失。完整保存会删除原消息再重写；增量保存也以压缩后的数组位置作为 seq，可能覆盖损坏行和后续原行。

**复现**：保存两条消息，把第一条 payload 改成不合法 JSON。`getAll` 正常返回仅一条消息，再 `save` 后库内只剩该消息，坏行原始材料已被删除。

**修改说明**：读取结果返回健康态/部分损坏态及稳定消息序号；损坏原文隔离保留。出现损坏时禁止普通覆盖保存，提供可读部分导出与明确修复流程。不要用数组压缩后的下标替代持久化身份。

**验收**：坏首行/中间行/尾行、未知新字段、旧格式不兼容、重启后继续发消息。原始坏行保留，正常行不移位覆盖，错误不暴露用户正文。

## A04：SSE 结束必须区别正常完成与异常 EOF

**位置**：`CloudProviderTools.parseOpenAIStream` / `parseAnthropicStream`，`CloudProvider.performStream`，`DispatcherEngine.chatStreamWithRetry`。

OpenAI 解析循环自然 EOF 后直接返回，Anthropic 也明确在未收到 `message_stop` 时返回累计内容。缺少结束原因时 `isTruncated` 为 false，上层可把残缺答复标为完成。流中的错误事件缺少专门处理；旧 `AsyncStream` 接口还会吞掉读取异常。工具参数只要没收到 `length/max_tokens`，也不会进入“残缺调用拒绝”分支。

**复现**：HTTP 200 SSE 只返回一段正文，然后正常关闭连接，没有完成标记或结束原因。`chatStream` 返回成功、正文为半段、`finishReason == nil`、`isTruncated == false`。

**修改说明**：建立协议解析状态，校验兼容提供商明确允许的终止条件，处理 SSE error 事件。异常结束抛带“已有部分内容”的领域错误，保留正文但标记中断；缺少可信完成状态的工具调用不执行。推理增量也应把请求标为已经开始，避免只有思考输出时重复请求。旧流接口改为可抛错且可取消的流。

**验收**：正常完成、只有 usage、正文后 EOF、工具参数后 EOF、错误事件、仅推理后断流。既不把半段标为成功，也不在交付增量后盲目重试。

## A05：畸形 HTML 可以触发非法 String 范围

**位置**：`WebFetchTool.extractTitle`。

代码分别找第一个 `<title>` 与最后一个 `</title>`，未检查闭标签位于开标签之后，随后构造字符串范围。输入 `</title>prefix<title>open without close` 会使范围上下界颠倒。工具输出截断不能防止解析阶段的异常。

**复现**：隔离单测直接调用真实提取函数，测试进程以 signal 5 退出，报 `Range requires lowerBound <= upperBound`。这是确定的进程终止，不是一个可捕获的普通工具错误。

**修改说明**：仅在开标签之后的范围内搜索对应闭标签；无合法闭合就返回空标题或安全降级。对解析器增加大小边界与恶意输入回归，后续可换为具有容错能力的 HTML 解析实现。

**验收**：闭标签在前、只有开标签、多标题、混合大小写、极长标题，均不终止进程。

## A06：操作日志必须有单一写入顺序，并且损坏时停止自动恢复

**位置**：`OperationJournal.init` / `persist` / `recordIntent` / `recordReceipt`；`DispatcherEngine.perform`。

锁只保护内存快照；编码与替换发生在锁外，多个 persist 可按相反顺序完成。原子替换防止半文件，却无法防止旧快照覆盖新快照。初始化时读取或解码失败又静默落为空字典，守护进程据此认为没有未决操作。回执写入返回值未被引擎处理。

**复现**：对同一日志并发提交 intent，所有提交都报告成功，重载后部分成功操作不在磁盘记录中。另向 operations.json 写入坏 JSON，初始化后 `isEmpty` 和未决集合均为空，甚至允许写新 intent 覆盖坏文件。

**修改说明**：

1. 用专属串行 I/O 执行器或 actor 排定“更新→持久化→确认”顺序，或改为事务化日志；不要把文件 I/O 放进 NSLock。
2. 引入版本号与加载状态，区分不存在、健康、损坏、不可读；损坏或不可读转人工恢复，保留文件。
3. 回执失败后禁止进入可安全移交/自动续跑状态；向用户展示结果不确定。
4. 回执复用同时保留 succeeded 与完整结果/截断标记，不能把失败回执重标为成功。

**验收**：人为让较旧写入最后完成；并发 intent/receipt；写失败后重启；日志损坏。凡已确认成功持久化的操作都必须仍在磁盘状态中。

## A07：Daemon 的领取、检查点与提交要成为完整协议

**位置**：`DaemonHandoffStore.acquireDaemonLock` / `records` / `updateState`；`DaemonMain.process`。

单例锁是先探测 PID 再写文件，两个实例可同时观察到无人运行并都领取成功。任务执行期间只更新 state，没有持续持久化新的引擎 snapshot；`committing` 也没保存待提交 outcome。重启从旧快照重新请求模型时，工具调用 ID 可能变化，旧回执无法按新 ID 去重。损坏任务记录会被扫描器直接删除。

这意味着已有 intent/receipt 机制还不能保证跨崩溃不重复执行；不能把“有状态机字段”等同于“完整恢复协议”。

**修改说明**：用持有文件描述符的系统排他锁抢占单例，任务再做原子领取。模型响应及稳定操作 ID 要先检查点化，再执行副作用；工具批完成继续持久化快照。进入 committing 前保存完整待提交结果，重启直接提交。状态写失败中止推进；坏记录隔离，人工恢复提供查看、核实、放弃入口。

**验收**：双实例同时启动；模型回复后/副作用后/回执后/提交前分别杀进程；注入新 toolCall ID；状态写失败。每条任务只被一个执行者领取，不因恢复而重新生成已完成操作。

## A08：发信结果未知需要持久化，不能只锁当前 Sheet

**位置**：`MailSyncService.send`，`MailDraft`，`MailComposeView` 的 `SendLock`。

超时会抛 `sendResultUnknown`，但草稿没有写入待核实状态；UI 的 `.unverified` 只在当前 Sheet 内存中。重开或重启后，只检查 `deliveredAt`，可重新发送，且生成新的 Message-ID。DATA 阶段连接重置目前还按普通失败处理。投递凭证与本地副本同时写失败时也无法可靠阻止跨重启重发。

**修改说明**：草稿或独立投递记录持久化 prepared/sending/accepted/unknown/localSaveFailed 状态、稳定 Message-ID 与尝试身份。进入可能投递的阶段前落盘；不确定结果必须持续阻止普通重试，提供核实后显式处置。SMTP 适配器报告阶段，只有确定未投递的错误才能显示“重试发送”。不要把 Message-ID 本身当作服务器保证的幂等键。

**验收**：服务器收下后断开回执、发信超时后关 Sheet/重启、凭证写入失败、同草稿并发发送。不会把未知结果转成普通可重试草稿。

## A09：不可逆投递应逐次硬确认

**位置**：`MailSendTool`，`DispatcherTool.roundAuthorizationKey` 默认实现。

`mail_send` 只有普通确认，默认授权键是工具名；一次“本轮允许”可覆盖该轮后续所有收件人、正文和账号。删除邮件已有硬确认，但发信没有单封收件人和单轮次数上限。

**修改说明**：发信启用 hard confirmation，禁用整工具的本轮授权；确认完整展示收件人/抄送/密送/内容。添加可解释的收件人数、批量投递预算与速率限制，且不可通过子代理或重建服务绕过。自动审核继续排除外发。

**验收**：同一轮第二次投递仍需确认；改变账号、收件人或密送不能复用前次批准；注入消息无法用一次授权连续群发。

## A10：会话导出保留了跨 suspension 的数组下标

**位置**：`ChatViewModel.loadFullSession`。

函数先保存 `idx`，等待 `getMessages` 后执行 `sessions[idx] = session`。期间用户可删除、新建或重排会话；下标可能指向另一会话或已经越界。同文件的 `refreshFromDatabase` 已使用“保存 ID，等待后重新定位”的正确做法。

**修改说明**：跨 await 只携带会话 ID 和请求世代，返回后重新查找；目标已删除则停止写回。再核对消息是否已经由新运行加载或修改，避免旧导出查询覆盖新内容。

**验收**：人为阻塞消息读取，删除目标/前一项、插入置顶会话、开始新一轮，再释放读取。导出不崩溃，不覆盖其他会话。

## A11：读写失败必须保留可恢复状态并对用户可见

**位置**：`loadMessagesIfNeeded` / `loadFullSession` / `persistSession`、会话重命名与隐藏路径。

消息读取失败经 `try?` 变成空数组并标记已加载，后续发送可把缺历史的状态写回。持久化失败只进入日志；用户仍看到完成答复，退出后才发现结果没有保存。重命名、隐藏等也存在吞错路径。

**修改说明**：加载状态改为 idle/loading/loaded/failed，失败不置 loaded，不允许据此覆盖历史。消息维护 dirty/persisting/persisted/failed 状态，写失败保留内存版本与受控重试，退出前提供明确选择。关键结果保存失败进入界面，而非只打印日志；UI 文案补齐三语。

**验收**：SQLite busy、磁盘写满、权限失败、短暂读取失败。界面能说明“尚未保存”，重试成功后清除，失败加载不成为空会话。

## A12：技能导入覆盖必须原子提交

**位置**：`SkillStore.importFolder` / `snapshotVersion` / `exportZip`。

覆盖前快照失败只记录警告，仍删除旧目录；然后 copyItem 失败就留下空目标。版本快照位于将被删除的技能目录内，不能作为独立恢复点持续保留。导出同样先删除已有目标，再尝试创建 ZIP，失败可能丢掉旧导出包。

**修改说明**：新技能先完整复制到同级暂存目录并校验；旧版本移到独立版本区；原子切换成功后再清理。覆盖前恢复点失败应中止覆盖。导出生成并校验临时 ZIP 后再替换。每个技能的写入需明确串行归属。

**验收**：复制中途失败、快照失败、同技能并发导入、覆盖中退出、导出失败。旧技能与旧 ZIP 始终可用，不依赖已删除目录里的快照。

## B01：索引候选检索与主线程快照是性能主线

**位置**：`ensureAllMessagesLoaded`、`EngineAssembly.build`、`SkillStore.list`、`SkillUsageLog`、`KnowledgeSearchTool.execute`。

搜索防抖后仍 `getAll` 加载全部正文，内存长期保留；技能组装位于 MainActor，逐个读取并解析 SKILL.md；技能别名缓存失效时也在主线程扫描。知识检索先取全部条目再排名。审计与用量日志还在锁内读写整个 JSON，违背短临界区规则。

**本次合成基线**：内存 SQLite 中 150 个会话、每会话 40 条 2 KiB 文本；文件系统中 500 个约 2 KiB 技能。每项重复五次，记录中位数及范围。此处不是完整 UI 基准，也未测峰值内存、p95 或冷磁盘读取。

| 操作 | 中位数 | 范围 | 解释 |
|---|---:|---:|---|
| `SessionService.getSummaries` | 1.05 ms | 1.01–1.08 ms | 摘要路径较轻 |
| `SessionService.getAll` | 36.27 ms | 35.36–38.08 ms | 仅加载/解码约为摘要的 35 倍，尚未计 UI 匹配与渲染 |
| `SkillStore.list` | 28.38 ms | 27.94–29.99 ms | 同步扫描超过常见一帧预算，当前组装点位于 MainActor |

**修改说明**：会话/知识/邮件按空间建设索引，数据库先返回有限候选 ID/摘要，再按需读正文。FTS5 是否满足中文召回要用固定中英文查询集验证，不能直接替换后默认认为有效。技能扫描在后台建立不可变快照，目录事件或保存操作使其失效；正文继续按需加载。日志改为单一串行持久化入口或增量表，禁止锁内 I/O。

**验收**：扩大数据集，记录输入到结果的 p50/p95、主线程占用与峰值 RSS；过期查询取消；切空间后索引和缓存无交叉；迁移失败可回到旧搜索入口。

## B02：邮箱同步与本地列表要能长期收敛

**位置**：`MailSyncService.sync`、`MailService.upsertMessages` / `searchMessages`、`MailViewModel.reloadMessages`。

增量同步只追更大的 UID，不收敛远端删除或已有邮件 flags；本地状态优先导致其他客户端的已读/星标变更不回拉。无 UIDNEXT 时仍以“批次不满”停止，稀疏 UID 可遗漏后续邮件。列表固定读默认前 200 条，没有续载；LIKE 通配符未转义，正文缓存没有总容量与淘汰策略。同文件夹 Message-ID 匹配查询也缺少对应复合索引。

**修改说明**：远端 UID 集合差异对账，使用显式 dirty flags/同步时间合并状态；无 UIDNEXT 时通过 UID 搜索获得真实候选，不以返回条数推断尾部。列表采用稳定排序的游标分页，给出更多结果入口。添加检索索引、字面查询转义、正文缓存上限与可重建入口。Message-ID 去重需承认该字段可能缺失或重复。

**验收**：另一客户端删除/标星；UID 稀疏及 UIDVALIDITY 变化；超过默认页大小；含 `%`/`_` 的字面查询；长期大量 HTML 正文缓存。

## B03：actor 不等于跨 await 的账号互斥

**位置**：`Hub.makeMailSyncService`、`EngineAssembly.build`、`MailSyncService`。

界面和引擎各建服务，各有 actor；即使复用同一个 actor，方法在 await 处仍可重入。同步、标记、移动、发信可交错；`send` 的“先查是否已投递、再发送”并不是原子领取。细粒度操作还各自新建连接并登录。

账号删除也分两次数据库事务执行：先清关联数据，再删账号。第二步失败时可能留下空账号；网络任务的迟到写回仍需失效保护，不能只补级联 SQL。

**修改说明**：建立绑定空间+账号的异步互斥/操作协调器，租约覆盖完整 await 生命周期，取消可靠释放；若 App/Daemon 同时操作，增加跨进程领取协议。发信使用草稿尝试状态的事务化 claim，账号清理与账号删除合并在单一事务。连接只在确定的生命周期内复用，不能靠 Hub 缓存空间服务解决。只读请求有限退避；不可逆写不盲目重试。

**验收**：UI/工具并发同步、同步中移动与删号、同草稿重复点击、App/Daemon 并发。统计连接次数和最大并发，确认没有重复投递或旧请求复活已删除账号数据。

## B04：取消与超时要抵达实际执行对象

**位置**：`TranscriptionService.run`、`MicRecorder`、浏览器等待循环、`AutoReviewService.withTimeout`、备份压缩与 Python 安装。

Speech 没有保留 recognitionTask，缺少取消/超时和 continuation 单次完成闸门。录音启动的检查与安装 tap 不是一个受控生命周期，停止还在锁内调用音频引擎和日志。浏览器轮询吞掉 sleep 的取消，已取消任务可能快速循环到超时，后续仍继续操作页面。自动审核可选 reviewer 用 task group 竞速，但 reviewer 不响应取消时组作用域仍等待它；当前没有注入 reviewer，这一项是潜伏风险。压缩子进程与部分安装路径也缺少取消传播。

**修改说明**：每项任务持有实际请求/进程句柄，以单一生命周期所有者处理结束、失败、取消；continuation 只完成一次。轮询显式检查取消并抛出，先取消再执行的入口拒绝副作用。超时应能主动中断底层对象；音频设备调用移出锁。

**验收**：取消发生在授权前/请求中/回调抵达后；Speech 最终结果与错误交错；浏览器加载中停止；不响应取消的 reviewer 替身；安装中停止。任务和进程最终退出，不出现双 resume 或忙循环。

## B05：全局库故障要有独立状态和有效重试

**位置**：`SpaceStore.init` / `queue(for:)` / `retryCurrentDatabase`，`Hub.providerService`。

全局库失败被写进两空间的 issues，但空间库成功打开会清掉该空间 issue。`globalQueue` 与 providerService 都是初始化时冻结的 let；“重试”只重开当前空间库，无法恢复全局 Provider 服务。用户可能看不到真正故障，或点击重试后仍不可用。

**修改说明**：全局故障与空间故障独立存储；重试按故障归属重建连接和组合依赖，并使相应 UI 模型失效。避免打开健康空间就清除全局故障；数据库打开与迁移的同步耗时另做启动基准。

**验收**：仅 global.sqlite 无法打开、仅一空间迁移失败、故障解除后重试。覆盖层原因正确，Provider 恢复可用，另一空间不被误判。

## B06：备份应准确声明范围，预检约束实际导入项

**位置**：`BackupService.export` / `plan` / `decodeSessions` / `decodeMemories`。

包只含会话、记忆和技能，不含知识、智体、聊天附件、工作区映射和邮箱数据，附件路径换机后也不能自动重建。预检只检查 manifest 列出的段，写入却独立读取固定文件和 skills 目录；没有强制验证新版必需段、导入项与声明的一一对应、解包总量或符号链接范围。

**修改说明**：先明确“部分备份”或“完整恢复包”的产品承诺；分阶段补充空间数据、附件相对引用与工作区重绑定。新版格式严格校验必需段、相对路径、条数/字节数及实际导入集合；旧格式明确兼容模式。解包前后限制总量、文件数和链接逃逸。不要把无密钥的 SHA-256 校验描述成来源认证。

**验收**：空目录恢复、换机路径、缺清单段、额外未声明段、异常链接、过大压缩包、磁盘写满，确保用户知道哪些内容没有备份。

## B07：后台作业完成与历史持久化是两个不同时间点

**位置**：`JobCenter.run` / `update` / `finish` / `persistHistory`；`JobHistoryTests.historyPersistsAcrossRestart`。

作业先更新并广播 succeeded，再进入 finish 写历史。正式测试等待 isFinished 后立即读取历史文件，实际捕获过“文件不存在”；定向复查通过，符合这个时序窗口导致的偶发失败。这与最初的沙箱权限失败不同，不能归为环境问题。已有串行历史写入与 revision 保护是正确基础，无需撤掉。

**修改说明**：明确作业工作完成和历史保存完成的契约；需要持久凭据的消费者等待显式持久化完成事件或 API。若产品承诺 succeeded 已经可靠保存，则增加 committing 状态并在落盘成功后发布最终状态。测试用完成屏障代替“观察内存成功就立刻读磁盘”；同时保留历史写失败的可观测状态。

**验收**：阻塞历史写入时观察状态，模拟写失败、立即退出/重启、并发 clearFinished。测试结果不依赖调度偶然顺序。

## C01：浏览器是否属于空间，应明确产品边界

`BrowserService.shared` 只有一套标签与固定 WKWebsiteDataStore，工具无 space 参数；切到工作空间仍能列出并读取个人空间打开的标签。当前文档把浏览器描述为共享登录会话，这是实际产品选择，不能未经确认就当作意外漏洞或直接清空登录态。

若空间承诺包含“投屏不暴露另一空间浏览记录”，应按空间隔离标签、Cookie/localStorage、活动广播和工具枚举，并处理两个缓存聊天模型同时接收浏览器活动的问题。若保留全局共享，界面需要明确说明该能力的归属，避免用户误以为整个应用数据都受空间隔离。

## C02：资源上限与可执行依赖完整性

网页抓取先把完整响应载入 Data、再截正文；图片也是先完整读取再检查 5 MB，因此输出上限不是内存上限。浏览器标签没有资源上限。Python 安装下载 latest 脚本后直接执行，且先删除已有运行时，没有固定发行版的可信校验与可回滚切换。

修改应包括：按 Content-Type 和实际接收字节限制流式下载；图片先 stat 并限长读取；浏览器空闲休眠/软上限保护活动任务；运行时固定版本、校验可信摘要/签名，在新目录完成验证后切换。实际内存与 WebContent 总资源曲线仍需专门测量，不能只用标签数推断泄漏。

## 实施顺序与交付要求

1. **数据保护批次**：A01/A02/A03/A11。先阻止串写、误删与隐形保存失败；迁移前建立独立恢复点。
2. **执行恢复批次**：A06/A07/A08/A09/B03。统一任务领取、稳定操作身份、发信状态与人工恢复；先做故障注入，再接 UI。
3. **崩溃与取消批次**：A04/A05/A10/A12/B04/B05/B07。小范围修复，加入可控延迟、断流、错误回调与目录故障回归。
4. **规模性能批次**：B01/B02/B06/C02。以本次合成基线为起点，补真实磁盘、长会话和大邮箱场景，按基准结果决定 DatabasePool 等较大结构调整。
